# ADR 0002: связь MCP-сервера с GUI

**Статус:** принято

## Контекст

MCP-клиенты (например, Claude Code) запускают MCP-сервер как дочерний процесс со stdio.
GUI — отдельное приложение Tauri. Требование: одна модель схемы, а изменения через MCP
сразу видны в GUI.

## Рассмотренные варианты

1. **Движок в отдельном процессе-демоне.** GUI и MCP — клиенты. Это третий процесс, у
   которого свой жизненный цикл, а Tauri пришлось бы поставлять вместе с Node-sidecar.
2. **MCP-сервер внутри Tauri (stdio).** Не подходит: клиент запускает свою копию
   процесса, а не подключается к уже открытому окну.
3. **Движок в webview, GUI-оболочка слушает loopback, MCP-сервер — тонкий клиент.**
   Выбрано.

## Решение

* Единственный экземпляр `Session` живёт в webview.
* Rust-оболочка открывает TCP на `127.0.0.1`, проверяет токен и пересылает запросы в
  webview событием `bridge-request`. Ответ возвращается командой `bridge_respond`.
* Порт и токен передаются через файл обнаружения в профиле пользователя.
* Протокол — NDJSON с версией (`protocol: 1`). Методы совпадают с именами инструментов MCP
  (`get_project_state`, `add_component`, …) и описаны Zod-схемами в
  `packages/core/src/api.ts`. Эти же схемы служат входными схемами MCP-инструментов,
  поэтому валидация одна для GUI-моста и для MCP.
* Если GUI не запущен, MCP-сервер не поднимает собственный движок, а возвращает ошибку
  `GUI_NOT_RUNNING`. Так исключается вторая независимая модель схемы. Для CI есть
  `openbench-headless` (`apps/mcp-server/src/headless-main.ts`) — тот же протокол без окна.

Жизненный цикл, обрывы и модель угроз описаны в [architecture.md](../architecture.md#ipc-gui--mcp).
