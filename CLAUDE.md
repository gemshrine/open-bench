# OpenBench — инструкции для coding-агента и техническое задание

> **Статус:** MVP specification (v1)  
> **Язык общения с заказчиком:** русский.  
> **Имя продукта:** OpenBench.  
> **Цель:** свободное настольное приложение для учебных лабораторных по архитектуре ЭВМ и цифровой схемотехнике: визуальный редактор схем, Word Generator, Logic Analyzer и управление через MCP.

## 0. Правила работы агента

Ты — ведущий разработчик OpenBench. Твоя задача — **реально реализовать и проверить работающий проект**, а не ограничиться планом, мокапом или декоративными кнопками.

1. Начни с изучения текущего репозитория; сохраняй и развивай существующий код. Если репозиторий пуст, инициализируй приложение.
2. Реализуй проект итеративно, начиная с **полностью работающего сквозного сценария**: добавить два входа → подключить AND → подключить выход к Logic Analyzer → управлять входами через Word Generator → увидеть правильную временную диаграмму.
3. После каждого этапа запускай проверку типов, линтер и тесты; устраняй ошибки. Команды, которые не удалось запустить, явно перечисляй.
4. Не делай фейковую симуляцию: показания приборов должны строиться по **той же модели схемы**, которую редактирует пользователь и изменяет MCP.
5. Не подменяй рабочие функции заглушками без явной маркировки. Не объявляй этап завершённым, пока не выполняются критерии приёмки.
6. Технические решения фиксируй в `docs/decisions/` (краткие ADR). Если выбор библиотеки/версии требует проверки, проверь её поддерживаемость и лицензию перед добавлением.
7. Применяй тесты к алгоритмам, особенно симуляции. Для UI добавляй хотя бы несколько e2e smoke-тестов.
8. По завершении каждого этапа выдавай: что готово, как запустить, какие проверки прошли, что осталось. Не заявляй об успехе без проверок.
9. Никаких платных API, облачной авторизации и обязательного интернета для работы программы. MCP работает локально.
10. Заимствование из EWB — **по функциям и общим UX-паттернам**. Не копируй проприетарные изображения, иконки, ресурсы, код или торговое оформление EWB. OpenBench — самостоятельный open-source продукт, не совместимый с ним по умолчанию.

## 1. Границы проекта

### Входит в MVP — обязательно

- Настольное приложение под актуальные Windows и Linux; macOS — желательно, если не мешает MVP.
- Графический редактор цифровых схем на сетке: палитра, добавление элементов, перемещение, выделение, масштаб, панорамирование, удаление, wires, соединение выводов.
- Элементы: `INPUT`, `OUTPUT`, `CONST0`, `CONST1`, `BUFFER`, `NOT`, `AND`, `NAND`, `OR`, `NOR`, `XOR`, `XNOR`. Для двухвходовых вентилей — два входа и один выход; у NOT/BUFFER — один вход. Базовый MVP ограничить этим набором.
- Word Generator: 16-битные слова (каналы `D0…D15`), список шагов, ручное редактирование битов/слов, `Step`, `Run`, `Stop`, `Reset`, циклическое воспроизведение `Cycle`; отображение текущего шага. Каждый канал доступен как источник сигнала на схеме.
- Logic Analyzer: 16 цифровых каналов (`CH0…CH15`), подключаемых к сигналам/сетям схемы; запись истории состояний и временные диаграммы с общей осью дискретного времени; масштабирование, курсор текущего шага, очистка истории.
- Моделирование комбинационной логики **с корректным вычислением выходов** и воспроизводимыми шагами времени.
- Сохранение и открытие проектов в собственном документированном JSON-формате (`*.openbench.json`), включая компоненты, связи, положение на холсте, Word Generator и конфигурацию Logic Analyzer. Явное версионирование схемы файла.
- Undo/redo для редактирования схемы, сообщения об ошибках подключения, горячие клавиши основных действий.
- Локальный MCP-сервер для программной сборки схем и управления симуляцией, работающий с общей доменной моделью.
- README с установкой, командами запуска, примером лабораторной и конфигурацией MCP для клиента.

### Не входит в MVP

Аналоговые цепи, SPICE, транзисторы, источники напряжения, осциллограф, печатные платы, Verilog/VHDL, импорт файлов EWB, облачный сервис, коллаборация, физически точные задержки вентилей, процессор как готовый компонент. Не добавляй их до завершения MVP.

### Опционально после MVP

Clock, D/JK/T/RS-триггеры, регистры, счётчики, шины/группы проводов, экспорт изображений и CSV сигналов, горячие клавиши и UI-мелочи под учебные сценарии. Последовательностную логику внедряй только с отдельной спецификацией тактов, начальных состояний и тестами; не смешивай её с моделью комбинационной логики в первой версии.

## 2. Технологический стек (предпочтительный)

- **Frontend:** React + TypeScript + Vite.
- **Desktop shell:** Tauri 2. Если интеграция с MCP через процессы в Tauri создаёт значительный блокер, задокументируй альтернативу, но не переходи незаметно на другой стек.
- **Стили:** CSS или лёгкий UI toolkit; чистый desktop-like интерфейс, удобный при разрешении 1366×768.
- **Core:** TypeScript-пакет без React/Tauri и DOM; чистые функции для графа схемы, проверки соединений, вычисления логики, Word Generator, истории сигналов и сериализации.
- **MCP:** актуальный официальный TypeScript SDK Model Context Protocol; локальный transport `stdio` для первого релиза. MCP-процесс и GUI взаимодействуют с одним работающим экземпляром движка через явно описанный IPC или локальный loopback API.
- **Tests:** Vitest для ядра; Playwright для сценариев редактора; дополнительные интеграционные тесты MCP.

**Важное ограничение архитектуры:** нельзя создавать две независимые модели схемы — одну в UI, другую у MCP. Один источник истины, единые команды и валидация. MCP должен менять открытую в GUI схему (или открывать/создавать её) с немедленным отображением изменений. Выбери конкретную схему IPC, задокументируй жизненный цикл процессов, разрыв соединения и поведение при закрытом GUI.

Предложенная структура (можно адаптировать с объяснением):

```text
openbench/
  apps/
    desktop/            # React/Vite UI + Tauri
    mcp-server/         # MCP stdio server
  packages/
    core/               # schema, commands, simulator, persistence
    shared/             # protocols/types if necessary
  docs/
    architecture.md
    decisions/
    mcp-setup.md
    examples/
  examples/
    and-test.openbench.json
  README.md
  LICENSE
  CLAUDE.md
```

## 3. UI и UX

Основной экран:

- Верхняя панель: New, Open, Save, Undo, Redo, Run/Pause/Step/Reset, масштаб.
- Левая палитра: логические элементы и приборы.
- Центральное поле: бесконечная или достаточно большая сетка с проводами и выводами. Символы логических элементов различимы и подписаны; провода не должны соединяться лишь потому, что пересеклись геометрически.
- Правая панель: свойства выделенного элемента/источника, информация о соединении и ошибки.
- Докируемые/плавающие окна приборов: Word Generator и Logic Analyzer, которые можно открывать рядом со схемой.
- Светлая тема по умолчанию. Интерфейс может напоминать инженерный редактор 1990-х по плотности и компоновке, **но не копирует ресурсы EWB**.

Минимальные взаимодействия: drag-and-drop из палитры; click-to-place; привязка к сетке; рисование провода от одного вывода к другому с визуальным подтверждением; Esc для отмены операции; Delete для удаления; Ctrl+Z/Y для undo/redo; Ctrl+S для сохранения; переключение значений INPUT. Показать состояние сетей цветом/подписью (0/1/ошибка/неизвестно), не полагаясь только на цвет.

## 4. Доменная модель и семантика симуляции

### Структура

- `Circuit`: schemaVersion, id, title, components, nets/connections, instrument configs, viewport (опционально).
- `Component`: стабильный уникальный ID, тип, позиция, параметры, явно перечисленные pins с направлением `input | output`.
- `Net`: электрическая логическая сеть, которая соединяет один драйвер и любое число потребителей; явно хранить соединения pin IDs или нормализованное описание ребёр.
- `Signal`: для MVP допускаются `0`, `1`, `X` (неизвестный), плюс отдельное состояние ошибки конфликтующих драйверов. Не маскировать неопределённость нулём.

### Правила

1. Вентиль вычисляет выход согласно таблице истинности, включая документированные правила распространения `X` (например, `0 AND X = 0`, `1 AND X = X`).
2. Запрети/отмечай соединение двух выходов на одну сеть и другие некорректные связи. Разрешай fan-out одного выхода на несколько входов.
3. Вычисление не зависит от порядка расположения компонентов в массиве: топологический обход графа либо итерация до стабилизации с явным обнаружением циклов.
4. Неустойчивые/циклические комбинационные схемы не должны зависать — отображай диагностическое состояние.
5. На каждом симуляционном шаге сначала применяются входные сигналы Word Generator и ручные INPUT, затем вычисляются сети и только после этого фиксируется снимок Logic Analyzer.
6. Определи единую дискретную временную шкалу `tick` (целое число). Для MVP один шаг Word Generator = один tick. Не изображай реальные наносекунды и задержки, которых движок не поддерживает.
7. `Step` выполняет ровно один шаг, `Run` последовательно выполняет шаги с управляемой скоростью UI, `Stop` останавливает, `Reset` возвращает индекс последовательности/время к началу и очищает историю согласно явно описанной настройке.
8. Изменение схемы во время запуска либо безопасно сериализуется через очередь команд, либо временно останавливает симуляцию; выбранное поведение задокументируй.
9. Результаты симуляции должны быть детерминированными при одинаковом проекте, входных словах и последовательности команд.

## 5. Word Generator — точное ожидаемое поведение MVP

- Таблица с минимум 16 битами (`D15…D0`) и строками последовательности; редактирование слов в двоичном виде, желательно также hex.
- Добавление, дублирование, удаление и перестановка шагов; ограничение на число шагов должно быть разумным и явно показанным.
- 16 выводов на схеме логически представляют выходы генератора, каждый индекс битов закреплён документированно (`D0` = младший бит).
- `Step`: установить очередное слово на выходах, выполнить вычисление схемы, записать один кадр Logic Analyzer и сдвинуть указатель.
- `Cycle`: при достижении конца перейти к первому шагу; без `Cycle` — остановиться на конце.
- `Run` использует управляемую частоту отображения (steps/sec) и не пропускает вычисления без явно задокументированной политики.
- Пустая последовательность: показывать понятную ошибку вместо падения. Удаление последней строки либо блокируется, либо оставляет пустое состояние с пояснением.

## 6. Logic Analyzer — точное ожидаемое поведение MVP

- 16 каналов; каждый подключается к net/pin схемы, каналам Word Generator либо остаётся отключённым.
- Временные диаграммы в виде цифровых прямоугольных волн (0/1), и отдельное понятное обозначение `X`/ошибки; общая ось ticks, горизонтальная прокрутка, zoom.
- Снимок всех каналов на каждом симуляционном тике **после** вычисления логики. История не генерируется произвольными UI-таймерами вне движка.
- Подписанные каналы, возможность отобразить/скрыть канал, cursor и значение под курсором.
- Очистка истории, контроль памяти для длинных запусков (например, ограниченный буфер с индикацией усечения).
- Если канал не подключён — показать `—`, не притворяться, что он всегда 0.

## 7. MCP: инструментальное управление OpenBench

Локальный MCP-сервер предоставляет инструменты с валидируемыми JSON-схемами входа и структурированными ответами. Названия ниже — требуемый базовый API, допустимо добавлять инструменты, не ломая эти.

| Tool | Функция |
|---|---|
| `get_project_state` | Вернуть открытый проект, компоненты, соединения, состояние симуляции и ошибки |
| `new_project` | Создать пустой проект |
| `add_component` | Добавить элемент по типу и координатам; вернуть ID и pins |
| `move_component` | Изменить позицию элемента |
| `remove_component` | Удалить элемент и связанные соединения |
| `connect_pins` | Соединить именованные/ID выводы, валидировать драйверы и типы |
| `disconnect_pins` | Удалить заданную связь |
| `set_input` | Установить ручной INPUT в 0/1 |
| `set_word_sequence` | Установить последовательность 16-битных слов |
| `configure_word_generator` | Режим Cycle и скорость воспроизведения |
| `attach_analyzer_channel` | Назначить сети/вывод каналу CH0…CH15 |
| `simulation_step` | Выполнить N детерминированных тиков (с ограничением N) |
| `simulation_reset` | Сбросить симуляцию |
| `get_signal_values` | Прочитать текущие значения сетей и выводов |
| `get_analyzer_history` | Вернуть историю указанных каналов с диапазоном ticks |
| `save_project` | Сохранить проект в разрешённый путь / дать понятный результат |
| `open_project` | Загрузить проект и проверить schemaVersion |

Необязательные инструменты после основного API: `get_canvas_screenshot` (доступен только при открытом GUI), `export_analyzer_csv`, `get_validation_errors`.

### Контракт качества MCP

- Для каждого инструмента: входной schema validation, сообщения об ошибках с кодом/описанием, детерминированный результат и отсутствие неявного повреждения проекта.
- `add_component` возвращает существующие валидные `pin IDs`, чтобы агент не угадывал имена.
- `connect_pins` не допускает произвольных строк без проверки.
- Раздели ошибки «GUI не запущен», «проект не открыт», «недопустимый ID», «конфликт драйверов», «симуляция недопустима».
- Локальные интерфейсы управления слушают только `127.0.0.1`, если выбран socket/HTTP transport. Предусмотри защиту от произвольных веб-страниц (origin/auth token или Unix/domain socket; опиши модель угроз). Для MCP `stdio` не открывай сетевой порт без необходимости.
- Операции с файлами ограничь явной рабочей директорией или контролируемым пользовательским выбором; не позволяй MCP незаметно читать/перезаписывать произвольные файлы.
- Обязательно покажи в `docs/mcp-setup.md` реальную конфигурацию подключения Claude Code и пример использования, соответствующий текущей версии SDK/CLI.
- Добавь интеграционный тест: MCP создаёт схему, вызывает `simulation_step`, читает правильные сигналы и историю Logic Analyzer. Состояние синхронизируется с GUI.

## 8. Файл проекта и совместимость

- Определи `schemaVersion: 1` и описание JSON schema или Zod schema, включённое в репозиторий.
- Проверяй входные файлы при открытии; показывай структурированные ошибки, не роняй UI.
- Сохраняй атомарно, где возможно, чтобы не испортить проект при ошибке записи.
- Сохранённый и заново открытый проект должен воспроизводить эквивалентную схему и настройки приборов.
- Не обещай совместимость с `.ewb` или собственными форматами Multisim.

## 9. Обязательные проверки и приёмка

Ниже минимальная проверка перед объявлением MVP готовым.

### Таблицы истинности

Проверь тестами все сочетания 0/1 у двухвходовых AND/NAND/OR/NOR/XOR/XNOR и оба значения у NOT/BUFFER; отдельно тесты на `X`, fan-out, отсутствующий драйвер, два драйвера и комбинационный цикл.

### Интеграционный сценарий №1: AND

1. Создать проект; добавить Word Generator, `AND`, Logic Analyzer.
2. Подключить `D0 → AND.A`, `D1 → AND.B`; `AND.OUT → CH0`. Желательно вывести D0 на CH1, D1 на CH2.
3. Задать слова `0x0000`, `0x0001`, `0x0002`, `0x0003`.
4. Выполнить четыре `Step`.
5. Ожидать `CH0 = [0,0,0,1]`, `CH1 = [0,1,0,1]`, `CH2 = [0,0,1,1]`.
6. Те же значения должны отображаться графически и возвращаться MCP.

### Интеграционный сценарий №2: XOR

D0 и D1 подключены к XOR, его выход к CH0. Для тех же слов ожидается `CH0 = [0,1,1,0]`.

### Интеграционный сценарий №3: сохранение

Создать схему через GUI или MCP → сохранить → закрыть/открыть → убедиться, что положение элементов, провода, слова, каналы анализатора и результат симуляции совпадают.

### Интеграционный сценарий №4: синхронизация

Открыть GUI и MCP → через MCP добавить вентиль и соединения → увидеть обновлённую схему в GUI → через GUI изменить вход → получить корректное изменение сигнала через MCP.

### Definition of Done

- Desktop-сборка запускается на целевой ОС, приложение не требует интернета.
- Все обязательные компоненты добавляются, соединяются и моделируются.
- Word Generator и Logic Analyzer функциональны, а не являются статичными картинками.
- Три основных интеграционных сценария (AND, XOR, сохранение) и сценарий синхронизации проходят.
- MCP предоставляет базовые инструменты, ошибки валидируются, есть рабочая инструкция подключения.
- Команды `lint`, `typecheck`, `test`, `build` документированы и успешно проходят в поддерживаемой среде; неисполненные платформенные проверки честно указаны.
- README содержит скриншоты реального UI, минимальную инструкцию запуска и пример первой схемы.

## 10. Этапы разработки (не пропускать фундамент)

**Этап A — каркас и модель:** монорепо, desktop UI, shared core, компоненты, pins, nets, команды, сериализация, тесты логики.

**Этап B — рабочий редактор:** палитра, canvas, wires, соединение pins, свойства, Undo/Redo, сохранение/загрузка.

**Этап C — симуляция и приборы:** вычислительный движок, Word Generator, Logic Analyzer, real GUI waveforms, интеграционные тесты AND/XOR.

**Этап D — MCP и IPC:** инструменты, общий state engine, синхронизация GUI↔MCP, безопасность локального доступа, документация, end-to-end tests.

**Этап E — стабилизация:** обработка ошибочных схем, производительность, доступность, исправление UX, сборка Windows/Linux, скриншоты, итоговый README.

На каждом этапе оставляй проект в запускаемом состоянии. Сначала вертикально работающее MVP, затем косметика.

## 11. Требования к разработке

- TypeScript `strict: true`, избегать `any` и несогласованных дублирующихся типов.
- Чёткое разделение: domain logic → command handlers → IPC/MCP adapters → UI.
- Undo/redo только для редактирования проекта; не смешивать случайно с каждым tick симуляции.
- Нет автоматических обновлений и телеметрии без отдельного согласия пользователя.
- Исходники и зависимости должны допускать open-source распространение. Предпочтительная лицензия собственного кода: MIT, но проверь совместимость лицензий встраиваемых компонентов; не подключай чужой copyleft-код без осознанного выбора лицензии.
- Уважай производительность: схема из ~100 вентилей и ~1000 ticks должна работать без заметных задержек на обычном студенческом ноутбуке (ориентир, проверять бенчмарком; не выдумывать измерения).
- Документация на русском как минимум для README/инструкции пользователя; имена API и кода на английском.
